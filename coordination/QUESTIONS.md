# QUESTIONS — decision queue and recorded owner decisions

Protocol: `PROJECT.md`, "Question protocol". **Append-only**: new rows get added, existing rows
aren't rewritten (except closing the status once the owner/orchestrator has answered).

**Why this file matters more than it looks like it should.** A question that only lives in a
chat transcript is invisible to every other role and to the same role after `/clear`. This file
is the one place a role can find out what the owner already decided without having access to
someone else's conversation. Write both the question **and** the answer here — a queue of
unanswered questions is only half useful; the point is a durable decision record.

Use one table per batch of related questions (e.g. all questions from one review session), with
a consistent schema — pick **one** column layout and stick to it project-wide, since
`coordination/tools/build_index.py` expects a `Status` column by name. If a table genuinely
doesn't fit that shape (e.g. it tracks execution progress rather than a yes/no decision), that's
a sign it belongs in `ACTIVITY.md` instead, not a reason to invent a new QUESTIONS.md schema.

### П-2 — уточнение от APP (2026-08-27): что уже сделано и в чём осталась развилка

Условие хэндоффа «делать, если правка сводится к тому, чтобы опора считалась при фактическом ψ»
**уже выполнено в коде**: `CwModel.compute` зовёт `_apply(p)` до `_reference_db`, поэтому
`cal.source_psi_deg` попадает в опорный отсчёт. Технической работы по этой формулировке нет.

Осталась ровно та развилка, ради которой заведён П-2. Опора приколочена к θ₁ = θ₂ = 0 — к **оси
прибора**, а не к максимуму. При повёрнутом источнике максимум уезжает на ψ/2, и кривая
превышает 0 дБ (когерентный приёмник, 0.9 ТГц, сечение по θ₁):

| ψ источника | A(0, 0) | максимум сечения | где стоит |
|---|---|---|---|
| 0° | 0.000 дБ | +0.000 дБ | θ₁ = 0° |
| 10° | 0.000 дБ | +0.067 дБ | θ₁ = +5° |
| 20° | 0.000 дБ | +0.274 дБ | θ₁ = +10° |
| 45° | 0.000 дБ | +1.635 дБ | θ₁ = +23° |

Что стоит за каждым вариантом:

- **на ось прибора (как сейчас):** 0 дБ = нуль обеих шкал ротаторов. Показание сходится с
  сервисным расчётом и с записью в журнале стенда, но при наклонённом источнике оператор видит
  «пропускание больше 100 %». Запас над 0 дБ в шкале окна (`theme.DB_LIMITS`) заведён именно под
  это и держится решением владельца 27.08.
- **на максимум:** превышения 100 % не бывает никогда, зато 0 дБ перестаёт отвечать нулю шкал и
  уезжает вместе с ψ; два прогона с разным наклоном источника становятся несравнимыми по
  абсолютной величине.

Развилка содержательная, а не оформительская: скрещенная пара одинаковых WGP поляризационно
нейтральна и у дна воспроизводит состояние источника, а не ось второй решётки, — то есть «ось
прибора» и «максимум» здесь описывают разные физические опоры, а не два способа нарисовать одно.

**Вопрос владельцу — один:** что считать нулём децибел при ψ ≠ 0 — нуль шкал ротаторов или
максимум кривой? Работа по правке 3 остановлена до ответа, правка 4 сделана.

### П-2 — решение владельца (2026-08-27): нормировать на максимум

Опорой служит **максимум кривой**, а не отсчёт при θ₁ = θ₂ = 0. Что из этого следует для кода:

- превышения 100 % при повёрнутом источнике больше не будет ни при каком ψ; запас над 0 дБ в
  `theme.DB_LIMITS` теряет исходное назначение, но снимать его без отдельного решения не нужно --
  он ничему не мешает;
- 0 дБ перестаёт отвечать нулю шкал ротаторов и уезжает вместе с ψ. Два прогона с разным наклоном
  источника **несравнимы по абсолютной величине** -- это принятая цена, и сказать о ней в
  интерфейсе придётся: иначе оператор сравнит два протокола и получит разницу из ниоткуда;
- показание окна расходится с `service_calc`, который считает от `P_max` совмещённого положения.
  Опорную точку сверки из `CLAUDE.md` (−4.77 дБ при 40°/0°/0.8 ТГц) это не задевает: там ψ = 0, и
  обе опоры совпадают. Расхождение появляется только при ψ ≠ 0;
- проверка M2 приёмки («(0, 0) даёт 0 дБ и 100 %») верна лишь при ψ = 0 и требует пересмотра.

Переключатель опоры в интерфейсе остаётся пунктом 0.5.0 дорожной карты («выбор опоры
нормировки»), а не частью правки 3.

### П-1 — решение владельца (2026-08-27): поставка не onefile

Собираем **папкой** (`COLLECT` вместо одиночного `EXE`): Qt-DLL лежат отдельными файлами рядом с
`.exe`, и получатель может заменить их своей сборкой Qt — требование LGPL закрывается самой формой
поставки, а не обещанием. Что из этого следует:

- `build/gui.spec` сейчас onefile (`console=False`) и требует переделки — задание ушло APP
  (`HANDOFFS.md` 27.08); файл в зоне APP, ORCH его не правит;
- наружу уходит **zip-архив** каталога, и SHA-256 из плана релизов (§6 п.4) считается на архив.
  Требование контрольной суммы не снимается: получателю нужен способ проверить, что файл тот самый;
- в комплект по-прежнему кладётся `LICENSES.txt`, и к первому внешнему релизу в нём должны быть
  **полные тексты** лицензий, а не ссылки — для LGPL-3.0 это обязательное условие;
- ложные срабатывания антивирусов у поставки папкой обычно слабее, чем у onefile, — побочная
  выгода, а не причина решения.
