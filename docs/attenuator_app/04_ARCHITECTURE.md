# 04 — Архитектура: одно ядро, две оболочки

---

## 1. Принцип

**Одно физическое ядро на Python, один UI на React, две оболочки.**

```
                     ┌──────────────────────────────────────┐
                     │      thz_atten_core  (чистый Python) │
                     │  numpy/scipy, без I/O, без сети      │
                     │  model · forward · inverse · limits  │
                     └──────────────┬───────────────────────┘
                                    │  вызывается напрямую
                     ┌──────────────┴───────────────────────┐
                     │   FastAPI  (thz_atten_api)           │
                     │   /v1/attenuator/*                   │
                     └──────┬───────────────────┬───────────┘
                            │                   │
              ┌─────────────┴──────┐   ┌────────┴───────────────────┐
              │  ВЕБ: браузер       │   │  DESKTOP: Tauri-оболочка   │
              │  React SPA          │   │  тот же React + sidecar    │
              │  сервер в облаке    │   │  FastAPI на 127.0.0.1      │
              │  без доступа к железу│  │  + драйверы ротаторов      │
              └─────────────────────┘   └────────────────────────────┘
```

Причина именно такого выбора: `github.com/brattri3/tydex-products-toolkits` уже построен на
**FastAPI + React + TypeScript + Vite + Tailwind + Recharts**, имеет модуль **Attenuator
Studio**, слой `backend/physics/` (`jones.py`, `stokes.py`, `solver.py`, `objectives.py`,
`analysis/attenuator.py`) и каталог калибровок `backend/data/calibrations/<серийник>/`.
Совпадение стека делает интеграцию «подпрограммой» вопросом переноса роутера и панелей,
а не переписывания.

**Разница desktop vs web — только в оболочке и в возможностях железа**, не в физике и не в UI.

| | Web | Desktop |
|---|---|---|
| Оболочка | браузер | Tauri (Rust webview) + sidecar-процесс FastAPI |
| Где считает | сервер | `127.0.0.1`, полностью офлайн |
| Драйверы ротаторов | ❌ (или через локальный агент) | ✅ pyserial / Thorlabs APT / Standa |
| Файлы измерений | загрузка через браузер | прямой доступ к каталогу прибора |
| Лицензия | серверная | офлайн-RSA, как в текущем продукте |
| Сборка | `vite build` | `tauri build` + PyInstaller-onedir для sidecar |

Альтернативы, отвергнутые сознательно: **Electron** (тяжелее Tauri в 5–10× по дистрибутиву
при том же результате); **PySide6/Qt** (быстрее для одиночного desktop, но даёт вторую
кодовую базу UI и хоронит переиспользование в вебе); **Pyodide** (физика в браузере —
заманчиво, но `lmfit`/фит калибровки туда не влезут комфортно, а разделять модель между
Python и WASM — гарантированное расхождение чисел).

## 2. Модули ядра `thz_atten_core`

```
thz_atten_core/
├── grid.py           t⊥, t∥ Бланко: векторизованно + LRU-кэш   ← model_core.py:blanco_t
├── drude.py          поверхностный импеданс металла             ← model_blanco.py:17
├── dressing.py       рассеяние ν^γ, утечка η(ν), τ_leak, τ_par + СОФТ-КЛИП (01 §3.3)
├── jones.py          J(φ), цепочки элементов, проекция на d     ← model_2wgp.py:jones
├── schemes.py        S1…S8: сборка цепочки по идентификатору    ← 03_OPTICAL_SCHEMES.md
├── forward.py        A(θ₁,θ₂,ν); A_int по весу w(ν); эллиптичность, азимут
├── weights.py        w(ν): из bg-файла | пресет источника | окно | гаусс
├── inverse.py        аналитическое начальное приближение + Брент + перебор ветвей
├── limits.py         F1…F8, A_floor, DR(ν), dA/dθ, σ_A          ← 02_SCENARIOS.md §4
├── uncertainty.py    J·Σ·Jᵀ + член формы модели + огибающая по γ ← 01 §3.4
├── zones.py          ν_anom = c/P; зелёная/жёлтая/красная
├── calibration.py    фит по измерениям → паспорт + ковариация   ← t20_weighted_fit.py
├── passport.py       чтение/запись/версионирование паспорта      ← 05_API_AND_FORMATS.md
└── io_tds.py         парсер .txt/.da, FFT, вычитание dark, усреднение повторов
```

**Инварианты ядра** (проверяются тестами, не соглашениями):
- никакого I/O кроме `io_tds`/`passport`; никакой сети; никакого matplotlib;
- все углы — градусы, **ориентация оси пропускания** (провода = угол + 90°);
- все частоты — ТГц; длины — микрометры на границе API, метры внутри Бланко;
- всякая возвращаемая величина затухания сопровождается `sigma_db`, `zone`, `extrapolated`;
- детерминированность: одинаковый вход → бит-в-бит одинаковый выход (кэш не влияет).

## 3. Приёмочные тесты ядра — переиспользуются готовые

`research/two_wgp/model_2wgp.py:selftest()` уже содержит 10 проверок, все проходят.
Переносятся в `tests/test_core_physics.py` как есть:

| Проверка | Ожидание | Достигнуто в research |
|---|---|---|
| сохранение энергии `Σ|E_out|² ≤ 1` | ≤ 1 | 0.9988 |
| закон Малюса в идеальном пределе | 0 | 6.7e-16 |
| Малюс с детектором на анализаторе | 0 | 1.3e-15 |
| идеальный предел == продакшн одно-WGP модель | 0 | ровно 0 |
| бит-сверка с `transmission_complex_two_polarizers` | 0 | 1.1e-16 |
| позиции пределов: argmax 0°, argmin 90° | — | ✅ |
| общий WGP2 == явно продублированный | 0 | ровно 0 |
| теорема выравнивания | < 1e-14 | 4.4e-16 |

Плюс новые, специфичные для приложения:

- `cos⁴θ` в идеальном пределе воспроизводится на сетке углов до 1e-12;
- относительный режим **не зависит** от `loss_factor` и `γ` (проверка сокращения из
  `02_SCENARIOS.md` §2.2) — важнейший тест, ловит регрессии в `dressing.py`;
- `A_floor` монотонно убывает с ростом `η`;
- обратная задача: `inverse(forward(θ)) == θ` на всей монотонной ветви, ±0.001°;
- F1…F8 срабатывают на подготовленных вырожденных паспортах;
- софт-клип: `dressing(ν)` ограничен и непрерывен вместе с производной в `f_hi`;
- золотые файлы (`golden/`) — численные регрессии по трём реальным паспортам.

## 4. Слои UI

Общий React-код (переиспользует компоненты `AppCard`, `AppTabs`, `AppStatCard`, `PlotPanel`
существующего продукта):

```
Панель 1  ПРИБОР       выбор паспорта, серийник, полоса калибровки, ER, η, D_eff/D_phys
Панель 2  СХЕМА        S1…S8 картинкой; ψ, φ₂, d, тип детектора, DOP
Панель 3  ИСТОЧНИК     w(ν): файл bg | пресет | окно | гаусс + предпросмотр спектра
Панель 4  РЕЖИМ        Абсолютный / Относительный  +  [SET ZERO] [AUTO-ZERO] [AUTO-CROSS]
Панель 5  ЗАДАЧА       Прямая (углы → A)  /  Обратная (A → углы)
Панель 6  РЕЗУЛЬТАТ    число + σ + зона + флаги F1…F8 + предложенные средства
График A  A(ν)         кривая, коридор σ, зоны фоном, линия DR(ν), метка полосы калибровки
График B  A(θ)         реальная кривая vs идеальная cos⁴; точка решения; ветви
График C  A(θ₁,θ₂)     тепловая карта (только S2)
График D  Поляризация  азимут и эллиптичность на выходе vs частота (жёлтая зона)
Панель 7  ПРОТОКОЛ     журнал операций, экспорт CSV/JSON/PDF
```

Правила визуализации, вытекающие из физики:

- полоса калибровки **всегда отрисована** на графике `A(ν)` (вертикальные границы + заливка);
  всё за её пределами рисуется другим стилем (пунктир) — экстраполяция не должна выглядеть
  как измерение;
- коридор `σ` рисуется всегда, даже когда он узкий, — иначе его отсутствие за полосой
  будет незаметно;
- зоны применимости — фоновая заливка (зелёная/янтарная/красная), не иконка;
- идеальная `cos⁴` — тонкая серая опорная линия на каждом угловом графике;
- цвета/палитра — по правилам дизайн-системы продукта (`docs/DESIGN_SYSTEM_MANIFESTO.md`
  в `tydex-products-toolkits`).

## 5. Состояние и потоки

Клиентское состояние (Zustand, как `attenuatorStore.ts` в текущем продукте):

```ts
{ passport, scheme, source, referenceMode, zeroRef, task, result, log }
```

`zeroRef` — не эфемерное состояние UI, а **сохраняемая сущность**:
`{θ₁⁰, θ₂⁰, U₀, timestamp, method, θ_offset, passportVersion}`. Каждый результат в протоколе
ссылается на её `timestamp`. Без этого через неделю невозможно понять, от чего отсчитаны дБ.

Все расчёты — на сервере/в sidecar. Клиент не дублирует физику ни в каком виде
(иначе неизбежно разойдутся числа).

## 6. Драйверы ротаторов (только desktop)

```
thz_atten_hw/
├── base.py       RotatorDriver: home(), move_abs(deg), position(), is_busy(), limits()
├── simulated.py  эмулятор: шаг, люфт, шум, задержка — для разработки и тестов
├── standa.py     ximc
├── thorlabs.py   APT / Kinesis
└── serial_gcode.py  простой ASCII-протокол
```

Обязательные свойства драйвера, попадающие прямо в проверку **F4**: `step_deg`,
`backlash_deg`, `repeatability_deg`, `range_deg`. Без них решатель не может честно
оценить `σ_A` и обязан помечать результат как «точность неизвестна».

Правило движения: при развёртке уровней (S-8) ходить **монотонно, без реверсов** — люфт
на глубоких затуханиях даёт единицы дБ (см. таблицу крутизны в `02_SCENARIOS.md` §3.3).

Веб-версия железо не трогает; при необходимости — отдельный локальный агент, но это v2.

## 7. Интеграция в `tydex-products-toolkits`

Целевое размещение (совпадает с существующей структурой продукта):

```
backend/physics/attenuator2/      ← thz_atten_core как пакет
backend/api/routers/attenuator2.py
backend/api/services/attenuator2.py
backend/data/calibrations/<серийник>/passport.json
src/Attenuator2.tsx + src/components/Attenuator2*.tsx
src/locales/{ru,en}.json          ← ключи attenuator2.*
docs/ATTENUATOR2_*.md
```

Что **переиспользуется** из продукта без изменений: `physics/jones.py`, `physics/stokes.py`
(ввод состояния поляризации вектором Стокса — уже сделано), загрузка и FFT TDS-данных
(`analysis/tds.py`), система лицензирования, i18n, дизайн-система, компоненты `ui/`.

Что делается **заново и почему**: существующий `analysis/attenuator.py` строит модель на
расширенном законе Малюса `T(α) = T_p cos²(α−α₀) + T_s sin²(α−α₀)` с тремя
феноменологическими константами на одну частоту. Этого достаточно для калибровки в точке,
но **принципиально не экстраполируется**: `T_p` и `T_s` не связаны с геометрией, поэтому за
пределами измеренной полосы говорить нечего. Новое ядро строит те же `T_p`, `T_s` из
`P`, `D_eff` и импеданса металла — и именно поэтому имеет право считать вне полосы.

Стратегия сосуществования: новый модуль **дополняет**, а не заменяет Attenuator Studio.
Старый — «калибровка и управление по измеренным точкам»; новый — «физическая модель,
экстраполяция, границы применимости». Общий формат паспорта позволяет старому модулю
отдать точки, а новому — подогнать по ним физические параметры.

Уже написанная в продукте спецификация `docs/tasks/attenuation_modes_spec.md`
(режимы `reference_mode: "input" | "zero_angle" | "parallel"`, поля `reference_intensity`
и `actual_db_relative`) **согласуется** с §2 документа `02_SCENARIOS.md` — контракт
относительного режима переносится один в один, чтобы UI не пришлось переучивать.

## 8. Нефункциональные требования

| Требование | Значение | Как достигается |
|---|---|---|
| Отклик прямой задачи | < 50 мс на 1000 частот | LRU-кэш Бланко по `(ν-сетка, P, D, N, Друде)`; векторизация |
| Отклик обратной задачи | < 200 мс | аналитическое начальное приближение + Брент, не Nelder-Mead |
| Карта `A(θ₁,θ₂)` 181×181×64ν | < 2 с | broadcast, `t⊥/t∥` считаются один раз на сетку частот |
| Офлайн desktop | полный | sidecar на `127.0.0.1`, нет внешних запросов |
| Воспроизводимость | бит-в-бит | закреплённые версии numpy/scipy, золотые тесты |
| Языки | RU/EN | i18n продукта |
| Единицы | ТГц, градусы, мкм, дБ | конвертация только на границе API |

Замечание по кэшу (важное, взято из `model_core.py`): **ключ кэша — точные биты float**,
без округления. При численном якобиане параметры возмущаются на ~1e-8 относительных;
округление ключа склеит соседние точки и испортит производную — это уже было предметом
отдельного комментария в исследовательском коде.
